# design-board — 시안 단계 안내 (/design 지시문)

시안은 **Owner가 직접 `/design` 명령으로 만든다.** 이 스킬은 시안을 직접 만들지 않고 아래 세 가지를 한다.
1. 회차마다 `/design`에 붙여 넣을 **지시문**을 만들어 준다 (design.md·기획서를 읽고 시안을 만들라는 내용).
2. Owner가 고르는 과정을 **안내**한다 (몇 안을 고르는지, 무엇을 보고 고르면 되는지).
3. 고른 안과 이유를 **기록**하고, 확정 후 저장 파일과 명도 대비를 **점검**한다.

이렇게 나눈 이유: 시안 생성은 Owner가 화면을 보며 직접 다루는 편이 빠르고 확실하다. 이 스킬은 지시문을 정확하게 만들어 매번 같은 규칙(design.md)이 적용되게 하고, 결정 기록을 남기는 데 집중한다.

Owner는 코딩 초보자다. 용어는 쉽게 쓰고, 지시문은 **코드 블록 하나에 통째로** 넣어 한 번에 복사할 수 있게 한다.

## 기본 회차

| 회차 | 시안 | Owner가 하는 일 |
|---|---|---|
| 1회차 | **5안** (A~E) × 대표 화면 1개 | 3안 고르기 |
| 2회차 | 고른 **3안** × 3화면 | 1안 고르기 |
| 최종 | 고른 **1안** × 모든 화면 + 주요 상태 | 수정 요청 → "확정" |
| 저장 | 확정 안을 프로젝트 파일로 저장 | 저장 지시문 입력 |

개수는 기본값이다. "B와 D를 섞어 줘", "A를 더 밝게" 같은 요청이 오면 새 이름(F, G…)으로 추가하는 지시문을 만든다.
시안 이름(A, B, C…)은 회차가 바뀌어도 유지한다. Owner가 "B랑 D 남겨"처럼 쉽게 말할 수 있다.

## 진행 순서

### 0. 준비 (지시문을 만들기 전)
1. `docs/PLAN.md`와 프로젝트 루트의 `design.md`를 읽는다. `design.md`가 없으면 하네스의 `rules/design.md`(이 스킬 폴더 기준 `../../rules/design.md`)를 그대로 복사한다.
2. 아래를 표로 보여 주고 Owner의 확인을 받는다.
   - 화면 목록, **대표 화면 1개**(앱의 성격이 가장 잘 드러나는 화면), 2회차에 쓸 **화면 3개**, 플랫폼(휴대폰/PC/둘 다)
   - 브랜드 자산(로고, 지정 색, 글꼴)이 있는지. 없으면 "없음"으로 진행
   - 참고 자료가 필요하면 `design.md` 4장 규칙대로 요청한다 (로그인이 필요한 곳은 로그인 또는 캡처 요청, 안 되면 넘어감)
3. `templates/design-README.md`로 `design/README.md`를 만들어 위 내용을 적는다. 다음 세션도 이 파일로 이어서 진행한다.

### 1. 회차마다 반복
1. `templates/prompts/`의 해당 틀(`round1.md`, `round2.md`, `final.md`)을 채워 **지시문**을 만든다.
   - `{ }` 칸은 모두 실제 내용으로 바꾼다. 앞 회차에서 Owner가 고른 안과 의견을 그대로 넣는다.
   - 파일 경로는 프로젝트 기준 실제 경로를 쓴다.
2. Owner에게 아래 순서로 보여 준다.
   - 이번 회차 요약 한 줄 (예: "1회차: 5안 × 오늘 화면 1개")
   - 지시문 (코드 블록 하나)
   - 입력 방법: "/design을 쓸 수 있는 Claude Code 세션에서 위 블록을 통째로 붙여 넣으세요. `/design`만 입력했을 때 따로 입력 칸이 열리면, 첫 줄을 뺀 나머지를 붙여 넣으세요."
   - **이번 회차에서 볼 것** 체크리스트 (아래 "고르는 법")
   - 결과를 알려 주는 방법: "고른 안 이름 + 이유 한 줄 + 캔버스 링크(있으면)"
3. Owner가 결과를 알려 주면 `design/README.md`의 회차 기록에 **무엇을 만들었고, 무엇을 왜 골랐는지** 적고 다음 회차로 간다.
   이유를 말하지 않았으면 한 줄만 물어본다 (다음 회차 지시문에 반영해야 하기 때문).

### 2. 고르는 법 (Owner에게 회차마다 보여 줄 체크리스트)
- **1회차 (5 → 3)**: 첫눈에 이 앱의 목적이 보이는가 · 가장 중요한 버튼이 바로 눈에 띄는가 · 분위기가 사용자와 맞는가 · 5안이 서로 충분히 다른가 (비슷하면 "더 다르게" 재요청 가능)
- **2회차 (3 → 1)**: 화면 3개가 같은 앱처럼 일관적인가 · 정보가 많은 화면에서도 읽기 쉬운가 · 휴대폰 크기에서 버튼이 누르기 쉬운가 · 오래 써도 질리지 않을 것 같은가
- **최종 (확정 전)**: 빠진 화면·상태가 없는가 (빈 화면, 오류, 저장 완료, 되돌리기) · 글자가 잘 보이는가 · 고치고 싶은 곳을 구체적으로 말해 수정 요청 → 만족하면 "확정"
- 좋아 보여도 고르기 어려우면 "A의 색 + C의 배치"처럼 섞는 요청도 된다.

### 3. 확정 후 저장
1. `templates/prompts/save.md`를 채워 저장 지시문을 만든다. Owner가 시안을 만든 같은 세션에 붙여 넣는다.
   - 저장되는 파일: `design/brand.md`, `design/tokens.css`, `design/screens/*.html` (틀: `templates/brand.md`, `templates/tokens.css`)
2. 저장이 끝나면 이 스킬이 점검한다.
   ```bash
   python3 <이 스킬 폴더>/scripts/contrast.py --tokens design/tokens.css
   ```
   - 4.5:1 미달이 있으면 고칠 값을 제안하고 Owner 승인 후 고친다.
   - `tokens.css`에 틀의 모든 항목(색, 글자, 간격, 모서리, 그림자, 테두리, 모션, 화면 크기 기준, 레이어)이 있는지 확인한다.
   - `design/screens/*.html`이 `../tokens.css`를 불러 쓰는지 확인한다.
3. `design/README.md`에 확정 안과 점검 결과를 적고 커밋한다.
4. 마지막 보고: 확정 안 요약, 저장한 파일, 점검 결과, 남은 의견, **"다음: 설계"**.

## 하지 않는 것
- 시안을 직접 만들기 (Artifact 도구 등으로). Owner가 명시적으로 "네가 직접 만들어"라고 할 때만 예외
- Owner 대신 시안 고르기 (시험 실행처럼 Owner가 맡긴 경우는 예외. 고른 이유를 기록한다)
- 직접 보지 못한 시안·참고 사이트 내용을 추측해서 기록하기. 모르면 Owner에게 묻는다
- 앱 코드 구현 (개발 단계에서 한다)
