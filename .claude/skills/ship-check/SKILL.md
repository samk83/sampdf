# ship-check — 출시 전 점검

"완료"라고 말하기 전에 **실제로 돌려 보고** 확인하는 단계다.
이 점검표는 실제 경험에서 나왔다. 자동 테스트는 모두 통과했지만 Owner의 Windows PC와 최신 Chrome에서 결과 승인 후 화면이 하얗게 변했다.
원인은 개발 환경에서 재현되지 않는 브라우저 동작 차이였다. 그래서 테스트 통과만으로 끝내지 않고, 실제 사용 환경과의 차이를 따로 확인한다.

## 점검표

각 항목을 실제로 실행해서 확인한다. 실행할 수 없는 항목은 **"미확인"으로 표시하고 이유와 Owner가 확인할 방법**을 적는다.
확인하지 않은 것을 확인했다고 쓰지 않는다.

### 1. 기본 검사
- 프로젝트의 테스트, 타입 검사, 빌드, 린트 (있는 것 모두). 실패하면 원인을 고치거나 Owner에게 알린다.

### 2. 실제 실행과 클릭
- 앱을 실제로 실행하고(웹이면 브라우저 자동 조작) `docs/PLAN.md`의 주요 사용 흐름을 끝까지 따라간다. `run` 스킬이 있으면 활용한다.
- **PC 폭과 휴대폰 폭(약 390px)** 둘 다 화면을 캡처해서 직접 본다.
- 화면 오류(콘솔 오류, 하얀 화면), 가로 스크롤, 겹침, 잘림을 확인한다.

### 3. 실제 사용 환경 차이
- **대상 OS**: Owner는 Windows 11을 쓴다. 경로(`\`), 한글 인코딩(PowerShell 기본 창은 CP949), 파일 잠금, 실행 스크립트를 점검한다. 클라우드(Linux)에서 확인할 수 없으면 Owner가 한 번에 확인할 수 있는 점검 방법을 준비한다.
- **최신 브라우저**: 개발 환경의 브라우저가 Owner 브라우저보다 오래됐을 수 있다. 브라우저 API의 반환값에 기대는 코드(예: effect에서 값을 그대로 반환하는 코드)는 피하고, 화면 오류가 하얀 화면 대신 안내로 보이게 하는 안전망이 있는지 확인한다.
- **휴대폰 실기기·앱 스토어 빌드**가 필요하면 미확인으로 두고 확인 방법을 적는다.

### 4. 디자인 기준 (`design.md`)
- 명도 대비: 본문 4.5:1 이상. 토큰 파일이 있으면 계산 도우미로 확인한다.
  `python3 <하네스>/skills/design-board/scripts/contrast.py --tokens design/tokens.css`
- 휴대폰 주요 버튼 터치 영역 약 44px 이상
- 상태 화면: 로딩, 빈 화면, 오류, 성공 피드백이 있는지
- 파괴적 작업(삭제·초기화)에 확인 또는 되돌리기가 있는지
- 하드코딩된 색·간격 대신 `design/tokens.css` 변수를 쓰는지 (샘플로 확인)
- Reduced Motion 설정 존중

### 5. 안전
- 비밀번호·API 키·토큰이 코드나 커밋에 들어가지 않았는지
- 유료 API가 Owner 동의 없이 켜져 있지 않은지
- 지우거나 덮어쓴 Owner 파일이 없는지

### 6. 문서
- `docs/FEATURES.md`(기능 지도), `docs/DECISIONS.md`(결정), `CLAUDE.md`(진행 단계, 자주 쓰는 명령)가 이번 변경을 반영하는지

## 보고 형식

아래 형식으로 짧게 보고한다. Owner는 코딩 초보자이므로 용어는 쉽게 쓴다.

```markdown
## 점검 결과: {무엇을 점검했나}

| 항목 | 결과 | 근거 |
|---|---|---|
| 테스트·빌드 | ✅ 통과 | 테스트 42개 통과, 빌드 성공 |
| 실제 실행 (PC·휴대폰 폭) | ✅ | 주요 흐름 3개 끝까지, 화면 오류 0 |
| Windows 실행 | ❓ 미확인 | 클라우드는 Linux. 아래 명령으로 확인 필요 |
| 명도 대비 | ⚠️ 1건 수정 | 보조 글자 3.9 → 4.6 |

### 남은 문제
- {있으면}

### Owner가 할 일
{명령이 필요하면 한 칸에 한 줄씩, 각각 따로 복사할 수 있게 코드 블록으로 준다}
```

Owner가 실행할 명령은 **한 칸(코드 블록)에 한 줄씩** 준다. 여러 줄을 한 블록에 넣으면 복사·실행 실수가 생긴다.
